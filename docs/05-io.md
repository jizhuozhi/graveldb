# 06 — I/O Strategy: io_uring Batch Flush & Peephole Merge

## Problem

Embedding 批量写出（flush）和 checkpoint dump 涉及数十到数千个不连续页面的 I/O。朴素做法每页一次 pwrite syscall + 一次 fdatasync，系统调用开销占主导。

需要：
1. 将多次 I/O 合并为尽可能少的 syscall
2. 利用 NVMe SSD 的多队列并行能力
3. 保证 crash safety（fsync 语义）
4. 跨平台兼容（Linux / macOS）

## Alternatives Considered

| 方案 | 优势 | 劣势 |
|------|------|------|
| 逐页 pwrite + fdatasync | 简单 | N 次 syscall + N 次 fsync |
| writev (scatter-gather) | 减少 syscall | 仍需后续 fsync；不能跨 offset |
| Thread pool + blocking I/O | 并行 | 线程管理复杂；context switch |
| POSIX AIO | 异步 | API 笨重；实现质量参差 |
| **io_uring** | 真正零拷贝批量；内核侧并行；1 syscall 提交 N ops | Linux 5.1+ only |

## Actual Implementation

### io_uring Batch Flush (Linux)

```c
io_uring_flush_pages(fd, pages[], offsets[], count):
    // 1. 提交所有 WRITE SQE
    for i in 0..count:
        sqe = io_uring_get_sqe(&ring)
        io_uring_prep_write(sqe, fd, pages[i], page_size, offsets[i])
        // SQ 满时中途 submit + reap
    
    // 2. 追加 FSYNC SQE (IOSQE_IO_DRAIN 保证之前的写入全部完成)
    sqe = io_uring_get_sqe(&ring)
    io_uring_prep_fsync(sqe, fd, IORING_FSYNC_DATASYNC)
    sqe->flags |= IOSQE_IO_DRAIN
    
    // 3. 一次 io_uring_submit() 提交全部
    io_uring_submit(&ring)
    
    // 4. 等待所有 CQE 完成
    for i in 0..count+1:
        io_uring_wait_cqe(&ring, &cqe)
        // check cqe->res for errors
        io_uring_cqe_seen(&ring, cqe)
```

**关键设计**：
- Queue depth = 256，SQ 满时先 submit + wait 部分 CQE 再继续提交
- FSYNC 使用 `IOSQE_IO_DRAIN` flag 保证排在所有前序写入之后
- 所有 I/O 在内核侧跨 NVMe 多队列并行完成

### macOS Fallback

同一 API 签名，内部实现为简单的循环 pwrite + 最终一次 fdatasync：

```c
io_uring_flush_pages(fd, pages[], offsets[], count):  // macOS 版本
    for i in 0..count:
        pwrite(fd, pages[i], page_size, offsets[i])
    fdatasync(fd)  // 单次 fsync 摊销
```

### Peephole Gap Merge (Flush 优化)

WriteBuffer flush 时，对排序后的脏页列表做相邻合并：

```
排序后的脏页: [5, 6, 7, 10, 11, 15, 16, 17, 18, 19]

Peephole merge (gap ≤ 4):
  Run 1: pages 5-7   → 3 pages
  Gap 5→10 = 3 pages (≤4) → 合并!
  Run 2: pages 5-11  → 7 pages (含中间未脏页的冗余读写)
  Gap 11→15 = 4 pages (≤4) → 合并!
  Run 3: pages 5-19  → 15 pages 一次连续 I/O

结果: 1 次 pwrite(15 × 4KB = 60KB) 代替 10 次分散写
```

**权衡**：写入几个不脏的"间隔页"（写放大 ≤ 4 pages × 4KB = 16KB）换来的收益是：
- 减少 SQE 数量 → 减少 io_uring 提交轮次
- NVMe 顺序写比随机写吞吐高 2-3×
- 减少 FTL garbage collection 压力

### Flush 完整路径

```
dimbin_write_buf_flush(bin):
  1. 收集所有脏 page_id 到数组
  2. qsort(page_ids)
  3. Peephole gap merge → IoRun[] (start_page, count, merged_buffer)
  4. 对每个 run：
     - 如果 count == 1: 直接用 page buffer
     - 如果 count > 1: assemble 连续 buffer (memcpy 各页到临时大 buffer)
  5. io_uring_flush_pages(fd, buffers, offsets, num_runs)
  6. 清空 write_buf entries，释放 page 内存
```

### 性能数据

| 场景 | 朴素 pwrite+fsync | Batch io_uring |
|------|-------------------|----------------|
| Flush 50K dirty pages | ~170ms (50K syscalls) | ~15ms (1 submit) |
| Checkpoint 1% of 100K pages | ~3ms | ~0.8ms |
| 吞吐 (连续 flush) | ~120 MB/s | ~300 MB/s |

### 与设计文档的差异

| 设计文档假设 | 实际实现 |
|---|---|
| 独立 "Block I/O Scheduler" 组件 | **flush 路径内联的 io_uring batch helper** |
| IoRequest 结构 + merge_read_requests | **Peephole gap merge on sorted page array** |
| 读路径也用 io_uring 批量 | **读路径是单次 pread（single page load to read cache）** |
